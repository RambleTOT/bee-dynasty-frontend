## Безопасность

Подробно и с командами — `docs/SECURITY.md`. Сайт уже защищён на своей стороне: лимиты nginx, заголовки безопасности, `DELETE` через сайт закрыт. Ниже — то, что может сделать только бэк или владелец сервера.

### S1. SSH перебирают — P0

`PasswordAuthentication yes`, `PermitRootLogin yes`, за сутки — 20 130 неудачных входов, fail2ban нет. Готовый скрипт: `deploy/security/harden-server.sh` (fail2ban, файрвол; вход только по ключу — после того, как ключи всех лежат в `authorized_keys`).

### S2. Данные стенда может стереть любой — P0

На стенде `ALLOW_DESTRUCTIVE=true`, а пароль демо-учёток открыто написан в описании Swagger (`app/main.py`, `_DESCRIPTION`) и в гайде бэка. Любой может войти диспетчером и вызвать `DELETE /api/v1/data/scenarios` напрямую в `api.bee-dynasty.ru`.

- **Нужно:** в `.env` — `ALLOW_DESTRUCTIVE=false`, новый `DEMO_PASSWORD`, новый `JWT_SECRET` (иначе выданные токены живут ещё 21 день). Пароль убрать из описания Swagger и гайда, жюри передать отдельно.

### S3. Порт API открыт мимо nginx — P0

`http://185.166.196.106:8000` отвечает напрямую: без TLS и лимитов. Docker открывает опубликованный порт в обход файрвола.

- **Нужно:** в `docker-compose.yml` у `api` — `ports: ["127.0.0.1:8000:8000"]`.

### S4. Лимиты для `api.bee-dynasty.ru` — P1

Лимиты сайта не защищают API, открытый напрямую. Зоны уже объявлены в nginx, строки для конфига API — `deploy/nginx/api-limits.conf`: вход 10 в минуту, POST 60 в минуту, 20 запросов/с с IP.

### S5. CORS — P2

`Access-Control-Allow-Origin: *` для всех методов, включая `DELETE`. Фронту CORS не нужен (сайт ходит в API через свой домен). Достаточно `https://bee-dynasty.ru`, `:8443`, `:9443`.

## Открытые пункты

### P0

#### 21. Принятая версия теряет факты

- **Где:** «Принять изменения» (DS-07), ручное переназначение → дальше таймлайн и итоги диспетчера, календарь, экран инженера.
- **Сейчас:** план-результат перепланирования не несёт статусы точек и факты. На копии у версии 1 было 12 «Выполнена» и 5 «В работе», у принятой версии 2 — все 67 «Запланирована». С правкой п. 3 день, календарь и `/me/day` читают принятую версию: «Выполнено 0 из 67», а инженер на уже выполненной заявке получает `409 ILLEGAL_TRANSITION` «Нельзя выполнить 'en_route' из статуса 'done'» (статус в сценарии остался `done`). Автопрогон часов вернёт плановые факты только при следующем переводе часов; нажатия инженера (`actual_*`) пропадают совсем.
- **Нужно:** при сохранении версии (`persist_replan` и `/reassign`) переносить из прежней версии в точки новой `status`, `actual_arrival`, `actual_start`, `actual_end` по `request_id`. Если заявка ушла другой бригаде, факт (`done`, `in_progress`, `en_route`) тоже сохраняется.
- **Проверка:** `GET /planning/{новая}` → те же 12 `done` и 5 `in_progress`, `/calendar` → `by_status.done = 12`.
- **Фронт пока:** показывает статусы принятой версии как есть; на `ILLEGAL_TRANSITION` у инженера пишет «Заявка уже в статусе «Выполнена». Обновили маршрут».

#### 14. Срочная заявка: свободная бригада «прибывает» раньше события

- **Где:** DS-07 «Срочная» и лента: «Авария №U-5887 → Бригада 11, прибытие 10:26», «реакция 0 мин» при событии в 12:30. То же у аварии оператора и в коде `b0c6195`.
- **Сейчас:** состояние бригад на момент события считается (`_execution_state`: `available_at = event_time`), но времена итогового маршрута у бригады без визитов идут от начала смены: `arrival = 10:26`, `start = max(arrival, window_start = 12:30)`, `reaction_min = start − event_time = 0`.
- **Нужно:** маршрут после события у каждой бригады начинается не раньше `event_time` — от последней замороженной точки или от старта. Для примера выше: выезд 12:30 → прибытие 12:56 → реакция 26 мин.

  ```json
  "scenario": {"urgent": {"order_id": "U-5887", "engineer_id": "E11",
                          "arrival": "12:56", "start": "12:56", "reaction_min": 26, "reaction_target_min": 120}}
  ```

- **Фронт пока:** показывает как пришло.

#### 13. После «Прервать» заявка остаётся текущей у инженера

- **Где:** инженер, «Прервать» → причина → тост «Отправлено диспетчеру. Можно ехать к следующей заявке». Шаг демо E-09.
- **Сейчас:** ветка `fail` меняет статус только у заявки сценария (`request["status"] = "cancel_pending"`), а `_build_day` берёт статус визита из точки плана, и `active_request_id` — первый визит `en_route` / `in_progress`. После `fail` `/me/day` отдаёт прерванную заявку «В пути» и текущей. В коде `b0c6195` не исправлено (проверено на копии).
- **Нужно:** в ветке `fail` менять и точку плана:

  ```python
  new_status = "reschedule_pending" if reason == "client_reschedule" else "cancel_pending"
  request["status"] = new_status
  _update_visit_status(plan, request["id"], new_status, at)
  repository.save_plan(plan)
  ```

  Ожидаемый `/me/day`: `{"active_request_id": null, "visits": [{"request_id": "10232", "status": "cancel_pending"}, {"request_id": "10134", "status": "planned"}]}`. После «Отклонить» у диспетчера — вернуть точке прежний статус (баннер «Диспетчер вернул №… в план»).

- **Фронт пока:** после успешного `fail` держит у заявки «Отменяется» / «Переносится», пока бэк отдаёт `planned` / `en_route` / `in_progress` (до перезагрузки вкладки).

#### 15. Нет геокодера: точки заявок — хэш адреса

- **Где:** карта дня, маршруты, пробег («Сравнение», DS-05, итоги), карта инженера, авария оператора.
- **Сейчас:**
  - `beeline_import._geocode` ставит точку по хэшу адреса в пределах ±7 км от офиса;
  - `geo.demo_geocode` (авария оператора) — по хэшу в рамке Москвы. Пример: «г. Москва, ул. Юных Ленинцев, д. 50» → 55.562, 37.592 (~17 км от реального дома).

  В отчёте импорта это названо `geocoded_from_cache`. Точки на карте не совпадают с адресами, километры и сравнение с диспетчером считаются по условным точкам.

- **Нужно:** настоящий геокодер с кэшем в БД (адресов в CSV кейса ~200): HTTP Геокодер Яндекса (тот же ключ «JavaScript API и HTTP Геокодер», что для карты фронта) или Nominatim. Не нашли адрес — точка офиса, адрес — в `import_report.geocode_fallback`.

  ```text
  GET https://geocode-maps.yandex.ru/1.x/?apikey=…&format=json&geocode=<адрес>&bbox=35.1,54.2~40.3,57.0&rspn=1
  → pos "37.766 55.707" → latitude 55.707, longitude 37.766
  import_report: {"geocoded": 64, "geocode_fallback": ["…"], "geocoder": "yandex"}
  ```

- **Фронт пока:** показывает точки как пришли.

#### 17. Запись оператора на сегодня прячет день диспетчера

- **Где:** оператор записывает клиента на день, где уже есть демо или CSV → диспетчер открывает этот день.
- **Сейчас:** запись создаёт отдельный сценарий `source = booking`, а `GET /days/{date}` берёт самый новый сценарий региона. После первой записи на сегодня диспетчер видит день из одной заявки вместо демо-дня. Номера `BK-0001` начинаются заново в каждом таком сценарии, а отмена и перенос ищут заявку по номеру во всех сценариях — могут попасть не в ту запись. Гайд (§7) обещает «один сценарий на (регион, дата)» и `409 DATE_HAS_BOOKINGS` при импорте CSV. Обратного случая это не закрывает: запись на день, где уже есть CSV или демо, создаёт второй сценарий.
- **Нужно:** запись — в существующий день региона на эту дату. В начатом дне — встраивание событием `order_added` без пересчёта с нуля. Номер записи уникальный: `BK-20260928-0001` или сквозной счётчик.
- **Фронт пока:** ничего; на стенде записывали только на завтра в Югоцентр.

#### 18. Демо-день создаётся только при старте бэка

- **Где:** «Сейчас», календарь, инженер, авария оператора — на следующий день.
- **Сейчас:** `seed_demo_day` вызывается только в `lifespan`. Без перезапуска после полуночи демо-дня на новую дату не будет: диспетчер увидит пустой день, инженер — «План на сегодня ещё не опубликован».
- **Нужно:** создавать демо-день лениво — в `GET /days/{today}`, `/calendar`, `/engineers/me/day` и аварии оператора, если на сегодня дня нет (или раз в сутки планировщиком).
- **Фронт пока:** ничего.

#### 19. Одна отмена перекраивает полдня

На стенде: «Отмена №10036» — передано 16 заявок, «Бригада 2 недоступна» — 24, «Клиент отказался» по №10232 — 17 (из 66); новая бригада в коде `b0c6195` — 15 передач. Для диспетчера каждая передача — звонок инженеру.

Нужна «цена» передачи при перепланировании. Или сначала локальная починка: убрать заявку, вставить неназначенные, и только если не вышло — полный пересчёт. В `diff` — сколько километров даёт каждая передача.

### P2

#### 8. Стратегия `plan` для версии с поздним визитом

В коде `b0c6195` `strategies: ["plan"]` работает (98,0 км по той же методике, что FIFO). Но у версии после переназначения «с нарушением» (`force: true`) колонка `available: false` с заметкой «Infeasible route for E07»: отчёт не допускает опоздание. #### 20. Номер версии занимает отклонённое предложение

`persist_replan` присваивает предложению `version = version_seq + 1` сразу, а `apply` берёт этот номер. На копии: 1 → 2 → 4 (третий номер занял отклонённый вариант). Номер лучше присваивать при `apply` (действующий + 1). Фронт нумерует версии по цепочке без пропусков.

#### 22. Время в баннере инженера — UTC

`banners[].at` = `plan.created_at.strftime("%H:%M")` — это UTC («09:21» вместо «12:21»). Фронт время баннера пока не показывает; если понадобится — нужно московское время или часы дня.

#### 23. «Реальный диспетчер»: пробег по бригадам — нули

В `/planning/compare` у `dispatcher` `km_by_engineer[].km = 0.0` у всех бригад и `visits_total = 0` при `km_total = 472,9`. Колонки «Начато в окне» и «Просрочено» и пробег по бригадам фронт показывает как «—». Нужны километры по бригадам (оценка тем же расчётом, что `km_total`) и визиты для окон.
