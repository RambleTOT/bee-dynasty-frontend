## P0 — ломают демо

### 1. Нажатия инженера пишутся не в тот день

- **Где:** инженер, все кнопки: «Начать смену», «Отправиться в путь», «Взять в работу», «Выполнить», «Прервать», «Инцидент», «Не могу работать».
- **Сейчас:** `POST /engineers/me/actions` вызывает `engineer_action(scenario_id=None)`, а тот через `_resolve_scenario()` берёт **самый новый сценарий, где есть бригада с таким id**. Это может быть производный сценарий после события или день другого региона: у всех регионов бригады `E01…E12`. `GET /engineers/me/day` при этом читает день через `_me_scenario()` (регион + сегодня). Нажатие проходит (`200`), но пишется в чужой сценарий, и после опроса экран инженера откатывается.
- **Нужно:** чтобы нажатие меняло тот же день, который отдаёт `/me/day`. Контракт не меняется:

  ```text
  POST /api/v1/engineers/me/actions   {action, request_id?, payload?}
  → меняется день из _me_scenario(user) — тот, что отдаёт GET /engineers/me/day
  ```

  Правка в одну строку: в `me_action` передавать `scenario_id=_me_scenario(repository, user).id`.

- **Фронт пока:** обойти нельзя.

### 2. Инженеру закрыт `/auth/me` и `/auth/logout`

- **Где:** вход инженера и перезагрузка страницы.
- **Сейчас:** `role_allows('engineer', path)` пускает только на `/engineers/me*`, поэтому `GET /auth/me` и `POST /auth/logout` отвечают `403 FORBIDDEN`.
- **Нужно:**

  ```text
  GET  /api/v1/auth/me      → 200 UserOut {id, login, name, role, region_ids, engineer_id}  — для любой роли
  POST /api/v1/auth/logout  → 200                                                          — для любой роли
  ```

- **Фронт пока:** при `403` берёт профиль из claims токена; при выходе удаляет токен, даже если ручка вернула ошибку.

### 3. Новая версия плана после события не видна дню

- **Где:** шапка дня («Версия N»), баннер предложения, календарь; экран инженера после «Принять»; автопрогон часов; авария оператора.
- **Сейчас:** `persist_replan` создаёт новый сценарий на каждое событие, `/reassign` и `extend-resource`. Всё, что читает день, ищет план в **исходном** сценарии:
  - `GET /days` отдаёт прежний `active_plan_id` и не видит `pending_proposals` к новой версии;
  - `apply` считает `version` внутри производного сценария, поэтому номер снова 1;
  - `/engineers/me/day`, `/me/route`, нажатия (`_latest_plan`) — инженер не видит принятых изменений (новой аварии, переданных заявок);
  - `autoplay` находит 0 визитов;
  - `_resolve_operator_plan` не находит применённый план → авария оператора получает `409 DAY_NOT_STARTED`.
- **Нужно** (любой вариант):
  1. писать новую версию плана в **тот же сценарий** (заявки версии — в `input_payload` плана);
  2. или при `apply` обновлять у исходного сценария `scenario_metadata.active_plan_id` и `version` (сквозная нумерация по дню). Тогда `_overall_state`, `_latest_plan`, `autoplay` и `_resolve_operator_plan` берут план через этот `active_plan_id`, а предложения — как `proposed` с `parent_plan_id = active_plan_id`.

  Ожидаемый ответ `/days`:

  ```json
  {
    "date": "2026-09-28",
    "regions": [
      {
        "region_id": "east",
        "scenario_id": "<исходный>",
        "plan_state": "applied",
        "active_plan_id": "<действующая версия>",
        "version": 3,
        "pending_proposals": [
          {
            "plan_id": "…",
            "event_id": "…",
            "event_type": "urgent_order_added",
            "headline": "…",
            "created_at": "…"
          }
        ],
        "clock": "12:30"
      }
    ]
  }
  ```

- **Фронт пока:** диспетчер сам собирает цепочку версий по событиям (`GET /events` + `GET /planning` → `plan_id → result_plan_id`) и видит правильную версию и предложения. Инженеру, автопрогону и аварии оператора это не поможет.

### 13. После «Прервать» заявка остаётся текущей у инженера

- **Где:** инженер, «Прервать» → причина → тост «Отправлено диспетчеру. Можно ехать к следующей заявке». Шаг демо E-09.
- **Сейчас:** ветка `fail` в `engineer_action` меняет статус только у заявки сценария (`request["status"] = "cancel_pending"`). `_build_day` берёт статус визита из **точки плана** (`point["status"]`), а `active_request_id` — первый визит `en_route` / `in_progress`. Проверено на стенде (№10232, бригада E01): после `fail` `/me/day` отдаёт `10232: en_route`, `active_request_id: "10232"` — инженер снова видит прерванную заявку текущей с кнопкой «Взять в работу». Если он всё же поедет к следующей, текущей всё равно останется прерванная (она раньше по `sequence`). В коде 11:29 не исправлено.
- **Нужно:** в ветке `fail` менять и точку плана:

  ```python
  new_status = "reschedule_pending" if reason == "client_reschedule" else "cancel_pending"
  request["status"] = new_status
  _update_visit_status(plan, request["id"], new_status, at)
  repository.save_plan(plan)
  ```

  Ожидаемый `/me/day`: `{"active_request_id": null, "visits": [..., {"request_id": "10232", "status": "cancel_pending"}, {"request_id": "10134", "status": "planned"}]}`. После «Отклонить» у диспетчера — вернуть точке прежний статус (баннер «Диспетчер вернул №… в план»).

- **Фронт пока:** после успешного `fail` держит у заявки «Отменяется» / «Переносится», пока бэк отдаёт `planned` / `en_route` / `in_progress` (до перезагрузки вкладки).

### 14. Срочная заявка: свободная бригада «прибывает» раньше события

- **Где:** DS-07 «Срочная» и лента: «Авария №U-5887 → Бригада 11, прибытие 10:26», «реакция 0 мин» при событии в 12:30. То же у аварии оператора (`U-MUL0ZEYP`, прибытие 10:19).
- **Сейчас:** состояние бригад на момент события считается (`_execution_state`: `available_at = event_time`), но времена итогового маршрута у бригады без визитов считаются от начала смены (`shift_start` 10:00): `arrival = 10:26`, `start = max(arrival, window_start = 12:30)`. `reaction_min = start − event_time = 0`.
- **Нужно:** маршрут после события у каждой бригады начинается не раньше `event_time` (от последней замороженной точки или от старта). Для примера выше: выезд 12:30 → `arrival 12:56`, `start 12:56`, `reaction_min 26`.

  ```json
  "scenario": {"urgent": {"order_id": "U-5887", "engineer_id": "E11",
                          "arrival": "12:56", "start": "12:56", "reaction_min": 26, "reaction_target_min": 120}}
  ```

- **Фронт пока:** показывает как пришло.

### 15. Нет геокодера: точки заявок — хэш адреса

- **Где:** карта дня, маршруты, пробег («Сравнение», DS-05, итоги), карта инженера, авария оператора.
- **Сейчас:** `beeline_import._geocode` ставит точку по хэшу адреса в пределах ±0,06° широты и ±0,08° долготы от офиса (±7 км), `geo.demo_geocode` (авария оператора) — по хэшу в рамке Москвы. Пример: «г. Москва, ул. Юных Ленинцев, д. 50» → 55.562, 37.592 (Бирюлёво, ~17 км от реального дома; до бригады +20,7 км). В отчёте импорта это названо `geocoded_from_cache`. Точки на карте не совпадают с адресами, километры и сравнение с диспетчером считаются по условным точкам.
- **Нужно:** настоящий геокодер с кэшем в БД (адреса CSV кейса — ~200 шт.): HTTP Геокодер Яндекса (тот же ключ «JavaScript API и HTTP Геокодер», что для карты фронта) или Nominatim. Не нашли адрес — точка офиса и адрес в `import_report.geocode_fallback`.

  ```text
  GET https://geocode-maps.yandex.ru/1.x/?apikey=…&format=json&geocode=<адрес>&bbox=35.1,54.2~40.3,57.0&rspn=1
  → pos "37.766 55.707" → latitude 55.707, longitude 37.766
  import_report: {"geocoded": 64, "geocode_fallback": ["…"], "geocoder": "yandex"}
  ```

- **Фронт пока:** показывает точки как пришли.

  {"order_ids": ["305871133", "305869027"], "option": "add_engineer"}

- **Фронт пока:** считает только по кнопке «Рассчитать, кого не хватает» и сразу показывает полученное предложение в DS-07.

### 6. Добавить инженера в начатый день (§12)

- **Сейчас:** `POST /data/scenarios/{id}/engineers` после публикации → `409`.

  POST /api/v1/events/apply
  {"type": "engineer_added", "plan_id": "<действующий>", "source": "dispatcher", "apply": false,

  → 200 ReplanResult {status: "proposed", plan, …}   // в plan.routes — новая бригада с id

  Подойдёт и другой путь: `POST …/engineers` разрешён после публикации (бригада `available: false`), потом `engineer_available` → предложение.

- **Фронт пока:** после публикации формы добавления нет (флаг `addEngineerAfterPublish = false`).

### 7. Календарь не учитывает план

- **Где:** DS-01 — полоса статусов, «N не назначена».
- **Сейчас:** `GET /calendar` считает `by_status` по статусам заявок сценария, а `apply` их не меняет. После публикации все заявки дня — «Не назначена».
- **Нужно:** `by_status` по действующему плану: назначенные — `planned` и дальше по фактам, неназначенные — `unassigned`. Формат ответа тот же.
- **Фронт пока:** показывает как пришло.

### 8. Сравнение: «Наш план» по действующему плану

- **Где:** «Сравнение», DS-05, DS-10.
- **Сейчас:** `ours` перезапускает солвер (результат может отличаться от плана дня), `incremental` с `plan_id` отдаёт нули. Без `scenario_id` берётся последний загруженный сценарий любого дня.
- **Нужно:** `strategies: ["plan"]` (или исправленный `incremental`) — метрики маршрутов `plan_id` тем же расчётом, что `fifo` и `dispatcher`:

  ```text
  POST /api/v1/planning/compare {"scenario_id": "…", "plan_id": "…", "strategies": ["plan", "fifo", "dispatcher"]}
  → columns.plan = {available: true, engineers_used, km_total, unassigned, visits_total, started_in_window, late, km_by_engineer[…]}
  ```

- **Фронт пока:** «Наш план» берёт из `plan.summary` и считает окно и просрочку по маршрутам плана; `scenario_id` передаёт всегда.

### 16. Оператор не находит заявки дня

- **Где:** O-02 «Найти заявку» → «Отменить» / «Перенести».
- **Сейчас:** `GET /booking/requests` ищет только в сценариях `source = booking` (записи самого оператора). Заявки CSV и демо-дня не находятся: «10036» → `[]`. А `cancel` / `reschedule` ищут заявку по id во **всех** сценариях (`_find_request`, первый по дате создания — это может быть производный сценарий события) и пересчитывают день целиком (`planner.compute` с нуля, прежний план — `superseded`): для начатого дня теряются факты и часы.
- **Нужно:**
  1. поиск по исходным сценариям регионов пользователя (без производных), статус — по действующему плану;
  2. отмена / перенос заявки начатого дня — через событие, как у диспетчера: `order_cancelled` с `source: "operator"`, `apply: false` → предложение диспетчеру (текст тоста уже есть: «Чем занять освободившееся окно, решит диспетчер»). Для непочатого дня — как сейчас.

  ```text
  GET /api/v1/booking/requests?q=10036
  → [{"request_id": "10036", "region_id": "east", "date": "2026-09-28", "window": "16:00-18:00",
      "status": "planned", "engineer_name": "Бригада 10", "address": "…", "district": "…"}]
  POST /api/v1/booking/requests/10036/cancel {"reason": "client_refused"}
  → 200 {"request_id": "10036", "status": "cancel_pending", "plan_id": "<предложение>",
         "message": "Заявка отменена. Чем занять освободившееся окно, решит диспетчер"}
  ```

- **Фронт пока:** «Ничего не нашли. Проверьте номер или адрес».

### 17. Запись оператора на сегодня прячет день диспетчера

- **Где:** оператор записывает клиента на сегодня (или на день, где уже есть CSV) → диспетчер открывает этот день.
- **Сейчас:** запись создаёт **отдельный** сценарий `source = booking` на регион и дату, а `GET /days/{date}` берёт самый новый сценарий региона — после первой записи на сегодня диспетчер видит день из одной заявки вместо демо-дня. Номера записей `BK-0001` начинаются заново в каждом таком сценарии, а отмена и перенос ищут заявку по номеру во всех сценариях — могут попасть не в ту запись.
- **Нужно:** запись в существующий день региона на эту дату (демо, CSV или записи). Начатый день — встраивание событием `order_added` (без пересчёта с нуля), номер записи — уникальный (`BK-20260928-0001` или сквозной счётчик). `/days` не должен выбирать сценарий записи, если у региона на дату есть другой день.
- **Фронт пока:** ничего; на стенде записывали только на завтра в Югоцентр.

### 18. Демо-день создаётся только при старте бэка

- **Где:** «Сейчас», календарь, инженер, авария оператора — на следующий день.
- **Сейчас:** `seed_demo_day` вызывается только в `lifespan` при старте. Без перезапуска после полуночи демо-дня на новую дату не будет: диспетчер увидит пустой день, инженер — «План на сегодня ещё не опубликован».
- **Нужно:** создавать демо-день лениво — в `GET /days/{today}`, `/calendar`, `/engineers/me/day` и аварии оператора, если у региона по умолчанию нет дня на сегодня (или раз в сутки планировщиком).
- **Фронт пока:** ничего.

## P2 — мелочи

### 9. `headline` с именами бригад

`EventItem.headline` содержит id («Авария №U-0001 → E05»). Нужны имена: «Авария №U-0001 → Бригада Соколов, прибытие 13:25». Пока фронт собирает текст сам.

### 10. Ручное переназначение отдаёт `applied` и не гасит прежнюю версию

`POST /planning/{id}/reassign` сохраняет версию сразу `applied`, а прежняя тоже остаётся `applied`. Нужно: `proposed` (фронт сам вызовет `/apply`) либо корректное погашение прежней версии и `version + 1`. Пока фронт сразу зовёт `/apply`.

### 11. Район в окнах записи (9.7)

`GET /booking/slots?…&address=` → поле `district` в ответе. Бэк пока не делает (нет кэша геокодера); фронт район не подставляет.

### 12. Адрес офиса в отчёте импорта

`import_report.office.address` приходит с хвостом «;;;;;;» (пустые колонки CSV). Фронт обрезает.

### 19. Одна отмена перекраивает полдня

На стенде: «Отмена №10036» → передано 16 заявок, «Бригада 2 недоступна» → 24, «Клиент отказался» по №10232 → 17 (из 66). Для диспетчера каждая передача — звонок инженеру. Нужна «цена» передачи в перепланировании (или сначала локальная починка: убрать заявку, вставить неназначенные, и только если не вышло — полный пересчёт), и в `diff` — сколько км даёт каждая передача.

### 20. Номер версии занимает отклонённое предложение

В коде 11:29 `persist_replan` присваивает предложению `version = version_seq + 1` сразу, а `apply` берёт этот номер. После двух отклонённых предложений принятое станет «Версией 4» при действующей первой. Номер лучше присваивать при `apply` (действующий + 1). Фронт в DS-07 пишет «Версия N → N + 1».
