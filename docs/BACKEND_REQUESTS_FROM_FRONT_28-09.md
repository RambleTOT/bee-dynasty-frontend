# Ошибки бэка, найденные фронтом · 28.09.2026

Кому: Ваня. Нашли при подключении фронта. Код смотрели в образе с `api.bee-dynasty.ru` (выкладка 28.09, 09:41), воспроизводили на локальной копии бэка со своей SQLite; стенд не трогали. Подробности и обходы на фронте — в `docs/API_NOTES.md`, пп. 14–37.

## P0 — ломают демо

**1. Нажатия инженера пишутся не в тот день.**
`POST /engineers/me/actions` → `engineer_action(scenario_id=None)` → `_resolve_scenario()` берёт **самый новый сценарий, где есть бригада с таким id**. Это может быть производный сценарий после события или день другого региона: у всех регионов бригады `E01…E12`. А `GET /engineers/me/day` читает день по `_me_scenario()` (регион + сегодня). В итоге «Начать смену», «В пути», «Выполнить» уходят в чужой сценарий, экран инженера откатывается.
Правка: в `me_action` передавать `scenario_id=_me_scenario(repository, user).id`.

**2. Инженеру закрыт `/auth/me` (и `/auth/logout`).**
`role_allows('engineer', path)` разрешает только `/engineers/me*`, поэтому `/auth/me` и `/auth/logout` отвечают `403`. После перезагрузки страницы фронт не может узнать роль. Мы обошли это чтением профиля из токена.
Правка: добавить `/auth/me` и `/auth/logout` в разрешённые пути инженера.

**3. Версии после события живут в производных сценариях — день их не видит.**
`persist_replan` создаёт новый сценарий на каждое событие, `/reassign` и `extend-resource`. При этом:
- `/days` (`_overall_state`) смотрит планы только исходного сценария: после «Принять» отдаёт прежнюю версию и не видит предложений к новой;
- `apply` считает `version` внутри производного сценария, поэтому номер снова 1;
- `_latest_plan` в `/me/day` и нажатиях инженера, автопрогон часов (`autoplay`) и авария оператора (`_resolve_operator_plan`) ищут план исходного сценария. Итог: инженер не видит принятых изменений, автопрогон находит 0 визитов, авария оператора после первого принятого события получает `DAY_NOT_STARTED`.

Фронт сам собирает цепочку версий по событиям, так что диспетчер видит правильную версию. Инженеру и автопрогону это не поможет.
Правка на выбор: писать новые версии плана в тот же сценарий. Либо при `apply` обновлять у исходного сценария `active_plan_id` и `version`, а `_overall_state`, `_latest_plan`, `autoplay` и `_resolve_operator_plan` брать через него.

## P1

**4. CSV: `dispatcher_engineer_id` — имя бригады, а не id.**
После импорта в поле лежит «Бригада Горбанев», а id бригад — `E01…`. Стратегия `dispatcher` в `/planning/compare` не сопоставляет ни одной заявки: 0 бригад, 0 км, все неназначены. Колонка «Реальный диспетчер» на CSV-дне пустая. Правка: при импорте класть id бригады (`_engineers_from_control` уже строит соответствие).

**5. `/planning/compare`: `incremental` с `plan_id` отдаёт нули** (`engineers_used 0`, `coverage_pct 0`). Без `scenario_id` берётся последний загруженный сценарий любого дня. На фронте «Наш план» берём из сводки плана и всегда шлём `scenario_id`.

**6. `/calendar` → `by_status` не учитывает план.** Статусы берутся из заявок сценария, а `apply` их не меняет. После публикации плана календарь показывает все заявки «Не назначена».

**7. `extend-resource` при `apply: false` сохраняет версию `proposed`.** Она попадает в предложения дня. Поэтому рекомендацию «не хватает +N инженера» в DS-09 не вызываем.

## Мелочи
- `import_report.office.address` приходит с хвостом «;;;;;;» (пустые колонки CSV).
- `headline` в событиях содержит id бригад («→ E05»). Фронт собирает текст с именами сам.
- `created_at` на SQLite — без часового пояса.
